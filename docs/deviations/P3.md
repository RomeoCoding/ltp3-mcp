# P3 deviations from PLAN.md

1. `PeakEff` together with `NomEff` (49 outputs) is BLOCKED (`B-EFFICIENCY-MODEL`), as H12 says
   ("`PeakEff` ... select the model"). PLAN 6.1's closing sentence counts 387 `NomEff` outputs as
   "fully confirmed", which includes those 49. The two statements conflict; the solver follows the
   rule table because a wrong `complete=True` is worse than a wrong `complete=False`. To relax it,
   drop `PeakEff` from `_EFFICIENCY_MODEL_KEYS` in `solver.py`.
2. H11 (no efficiency key) blocks only outputs that have a consumer. An output nobody draws from
   has `Iout = 0`, so `Pin = 0` under every efficiency model we hold. H12 outputs block regardless,
   since a loss model may have a no-load term.
3. `A-CURRENT-PEAK-ONLY` is emitted for H4 although H4 is CONFIRMED: PLAN's P3 test requires the
   Artix-7 assumptions to be exactly `[A-CURRENT-PEAK-ONLY]`. `A-CURRENT-MODE` (H5) is emitted in
   `auto` mode only when a load has both currents and they differ.
4. Beyond the plan's codes: `A-CURRENT-FALLBACK` (no `Ipeak`, `Inom` used), `A-LDO`, `A-CASCADE`,
   `A-RESISTOR`, `A-NETLABEL`, and the `B-*`/`W-*` codes in `docs/SOLVER.md`.
5. Result shape is dataclasses (`SolveResult.to_dict()` gives the JSON of PLAN section 4) with
   extra fields `blocked`, `current_mode`, and per-load `i_value`/`unit_exp` for `format_oral`.
   `parts` lists Power/Converter/LDO/Load/Resistor only. When `complete` is False, `ploss_w` and
   `efficiency_pct` are `None` and `pin_w`/`pout_w` are partial sums.
6. `solve(graph, options)` takes a `TabGraph` (P2 interface) and a `SolveOptions` dataclass; the
   `current_mode` argument of the MCP tool maps to `SolveOptions.current_mode` in P7.
7. Display rounding defaults to half-up on the 15-digit text (oracle O5 is open) and is
   switchable with `SolveOptions.rounding`.
8. The `samples/` files are absent in this worktree; the Artix-7 oracle test reads the factory
   template from the template directory instead (`test_artix_oracle`).
